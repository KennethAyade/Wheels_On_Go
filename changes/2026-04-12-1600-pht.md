# 2026-04-12 16:00 PHT — Breathalyzer Rule Update + Unit-Safe Extraction

## Summary
Client delivered a new safety rule: any breathalyzer reading that reaches **0.05** is an automatic decline, **inclusive** of the boundary (the prior rule was strict-greater, `> 0.05`). The rule landed alongside a device change — drivers are now using a breathalyzer that reports in **g/L blood**, where older units in the pipeline were `%BAC` and `mg/L` breath. These three units are **not interchangeable** (`0.05 %BAC` ≈ `0.5 g/L`, an order of magnitude apart), so simply tightening the numeric threshold without teaching the system about the unit would have silently swapped pass/fail outcomes for roughly every driver.

This change fixes both problems: the threshold is now `>= 0.05 g/L` (inclusive, env-configurable), and Claude is asked to return the BAC value and its unit label **separately** so the backend can normalize to canonical g/L before the threshold check runs. The AI no longer decides PASS/FAIL — it only extracts what the device physically shows.

## Why this change

Before today:
- Claude was asked for a single `bacReading` number plus a PASS/FAIL verdict.
- The backend trusted the AI's verdict string and did not enforce the threshold itself.
- There was no notion of a unit. A value of `0.04` from a g/L device and a value of `0.04` from a `%BAC` device were treated identically, even though one is ~10× the other in real terms.

Two independent risks converged:
1. **Silent unit confusion.** New g/L devices in the field would produce readings that *looked* safe against the numeric threshold a `%BAC`-trained prompt expected (and vice versa).
2. **AI as safety decider.** A compliance-critical pass/fail gate was one prompt-drift away from changing behaviour. Fail-closed on *extraction* is easy to reason about; fail-closed on *judgement* is not.

The fix is to separate extraction (AI) from enforcement (code), and to make the unit explicit on every record so we can audit later.

## Client-confirmed design decisions

- **Unit:** `0.05 g/L blood` (literal device unit, near-zero-tolerance for professional drivers).
- **Boundary:** `0.05 exactly → FAIL` (inclusive; `>= 0.05` triggers the 8-hour cooldown).
- **Configurability:** env variable with `0.05` as the default, so the threshold can be tightened or loosened for future compliance changes without a code deploy.

## Unit normalization table (canonical unit: g/L blood)

| Device unit | Conversion to g/L blood | Notes |
| --- | --- | --- |
| `g/L` (blood) | identity (× 1) | Direct — new device units. |
| `%BAC` | × 10 | `0.05 %BAC = 0.5 g/L`. Legacy devices. |
| `mg/L` (breath) | × 3.2 | ≈ 1:2000 blood/breath partition ratio. `0.25 mg/L ≈ 0.8 g/L`. |
| anything else / null | — | → `INVALID_IMAGE` (fail-closed). |

## Backend changes

### `apps/api/src/verification/verification.service.ts`
- Added `BreathalyzerUnit = 'g/L' | 'mg/L' | '%BAC'` type and extended `BreathalyzerVerificationResult` with `bacValueRaw`, `bacUnitRaw`, `bacNormalizedGPerL`, `thresholdGPerL`.
- Constructor reads two new env vars with defaults:
  - `BREATHALYZER_FAIL_THRESHOLD_G_PER_L` (default `0.05`)
  - `BREATHALYZER_MIN_AI_CONFIDENCE` (default `0.7`)
- New Claude prompt: asks for `is_breathalyzer_device`, `is_reading_visible`, `bac_value` (number), `bac_unit` (enum), `confidence`, `reasoning`. Value and unit are extracted separately — the AI is not asked to judge the reading.
- `parseUnit()` canonicalizes common string variants (`"g/l"`, `"%"`, `"mg/l breath"`, etc.) to the enum; anything else returns `null`.
- `normalizeToGPerL(value, unit)`: identity for `g/L`, `× 10` for `%BAC`, `× 3.2` for `mg/L`, `null` for unknown.
- Threshold check is deterministic and lives in code: `normalizedGPerL >= this.breathalyzerFailThresholdGPerL ? 'FAIL' : 'PASS'`.
- `failClosed()` helper centralises the `INVALID_IMAGE` return path and ensures the new audit fields are always populated (even on error).

### `apps/api/src/checklist/checklist.service.ts`
- PASS/FAIL/INVALID_IMAGE branches persist the new fields on `BlowbagetsChecklist`: `breathalyzerBacUnit`, `breathalyzerBacNormalizedGPerL`, `breathalyzerThresholdGPerL`.
- Audit-log entry includes the unit, normalized value, and threshold-in-effect.
- The FAIL error message is now server-templated using the normalized number and the threshold snapshot, not hardcoded to `0.05`:
  `Reading: 0.06 g/L (above 0.05 g/L limit). You cannot accept rides for 8 hours.`

### `apps/api/prisma/schema.prisma` (BlowbagetsChecklist)
Added three nullable columns — nullable so existing rows don't require backfill:
- `breathalyzerBacUnit String?`
- `breathalyzerBacNormalizedGPerL Float?`
- `breathalyzerThresholdGPerL Float?`

Migration: `prisma/migrations/20260412160000_add_breathalyzer_unit_and_threshold_snapshot/migration.sql`.

### Config + deploy

- `render.yaml`: added both env vars as hardcoded `value:` entries (not `sync: false`) — the threshold is a client-visible compliance policy and should be source-controlled, not a secret.

## Testing

### `apps/api/test/verification.service.spec.ts` — 12 new tests
- **Fail-closed:** INVALID_IMAGE when unit is null, unrecognised (`"ppm"`), or AI confidence < threshold.
- **Threshold enforcement (default 0.05):** `0.04 g/L → PASS`, `0.05 g/L → FAIL` (boundary inclusive), `0.06 g/L → FAIL`.
- **Unit normalization:** `0.005 %BAC → 0.05 g/L → FAIL`, `0.02 mg/L → 0.064 g/L → FAIL`, `0.002 %BAC → 0.02 g/L → PASS`.
- **Configurable threshold:** env override `BREATHALYZER_FAIL_THRESHOLD_G_PER_L=0.03` causes `0.04 g/L` to FAIL; threshold-in-effect appears in the response for audit.

Test helper note — the `breathalyzerAiResponse(payload)` factory uses object spread over defaults (`{ ...defaults, ...payload }`) instead of `payload.bac_unit ?? 'g/L'`, because `null ?? 'g/L'` evaluates to `'g/L'` and would have silently converted the "null unit" test case into a "valid g/L" test case. This matters — any future extension of that helper needs to preserve the spread semantics or the fail-closed-on-null-unit coverage evaporates.

## What was deliberately not changed

- **Web admin reports** — the aggregate PASS/FAIL/INVALID_IMAGE counts in `AdminReportsService` are unit-agnostic and continue to work unchanged. Per-record drill-down (unit + normalized value + threshold snapshot) is now available in the database for future admin UI that wants to surface it; the current reports page does not.
- **The cooldown window** — remains 8 hours on FAIL, unchanged.
- **Biometric mock-mode guard** — this change is orthogonal to the 2026-04-12 0900 PHT Phase-A biometric guard widening; both coexist in staging.

## Rollback plan

If the rule needs to be reverted quickly:
1. Set `BREATHALYZER_FAIL_THRESHOLD_G_PER_L=0.06` (or higher) on Render — takes effect on next request, no deploy needed.
2. The fail-closed extraction path is independent of the threshold and should remain enabled regardless — reverting it would require code changes.

The database migration is additive (three nullable columns); rolling back the code without dropping the columns is safe.
